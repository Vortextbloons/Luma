# Luma plugin developer platform

Status · Implemented in the working tree. Live TV and paired-phone acceptance and resource budgets are open. See [the package contract](PLUGINS.md) and [the development guide](PLUGIN-DEVELOPMENT.md) for the current interfaces.

## Goal

A developer can scaffold a plugin, press F5 to run it in a disposable Luma instance, edit and reload it, and ship the same project as a normal Luma ZIP. An enabled plugin can contribute a Home card with an action that works with the TV remote. Use Weather as the first end-to-end example.

[PLUGINS.md](PLUGINS.md) describes the shipped contract. Today, developers typically create a ZIP and import it through Settings. Installed versions are immutable. API v1 supports declarative appearance, Home layout overrides, and phone remote panels. API v2 supports executable UI and background runtimes with explicit grants, and its executable packages cannot declare contributions or remote panels.

## Milestone 1 · Authoring and development host

Provide a `luma-plugin` CLI with `init`, `dev`, `validate`, and `pack`. Start with a TypeScript template and the Weather example. The template includes a build command, a manifest with schema completion, and a VS Code launch configuration that builds and invokes the development host. The host can be launched from a terminal, too. Document how to attach a debugger and inspect output.

- **Validate and pack.** Take a built package directory, report diagnostics with manifest field paths or package-relative filenames, and emit the existing `<id>-<version>.luma-extension.zip` format. Give the tooling a headless entry point into the Rust manifest and archive validators so Settings import, MCP staging, and CLI validation agree. Ship an editor JSON Schema and exercise it against the same manifest fixtures. Rust remains authoritative for file checks, package limits, and cross-field rules.
- **Start a disposable instance.** Add an explicit developer launch path in [native startup](../src-tauri/src/lib.rs). Resolve the profile before initializing persistence or Windows integrations. Give each session separate app data, plugin settings, grants, and instance identity. Keep normal tray, autostart, updater, remote listener, and MCP startup out of the development session by default. Identify the dev instance in the window and stop it with the CLI.
- **Reload a source folder.** Watch the built package output through the CLI. After a successful build, validate and snapshot the directory using the normal package rules, then replace the development session's active snapshot. Keep the last working snapshot and show diagnostics when validation fails. On a successful reload, tear down the old runtime and preserve compatible settings. Reuse approval within that session only when the plugin identity and requested access remain the same. Reapply normal access review when they change. Keep same-version replacement confined to the disposable profile.
- **Debug.** Surface build and validation errors in the terminal. Expose bounded per-plugin runtime logs, activation state, and bridge errors in the development session. Include the plugin ID and failing operation. Omit sensitive values and request contents from host diagnostics. Provide a development-only way to open DevTools for the active plugin surface.
- **Use the same API in development and production.** Publish a small typed SDK for the existing bridge operations, error responses, and subsequent command and event contracts. Reuse the bridge in [extension_spike.rs](../src-tauri/src/extension_spike.rs). Support plain JavaScript through the same protocol. Document permissions alongside each SDK operation.

## Milestone 2 · Home cards and on-demand commands

Introduce a proposed API v3 manifest variant that lets an executable plugin declare host-rendered Home cards and commands. Preserve v1 and v2 manifest interpretation. Keep appearance field ownership and dynamic card registration independent so adding a card cannot claim existing Home settings.

- **Manifest and compatibility.** Add an explicit host-version requirement for v3 and stable local IDs for cards and commands. Namespace them by plugin ID at registration. A Home card declares a title and one command defined by the same package. Validate references, uniqueness, resource limits, and supported runtime kinds. Display an actionable compatibility reason for packages the host can read but cannot enable.
- **Registry and lifecycle.** Extend [plugin.rs](../src-tauri/src/customization/plugin.rs), [the archive layer](../src-tauri/src/customization/plugin/archive.rs), and [MCP schemas](../src-tauri/src/customization/mcp.rs). Project only compatible, enabled contributions to the UI. Update the registry after enable, disable, replacement, or removal through existing plugin change notifications. Keep MCP validation and staging separate from runtime execution. Disk and database changes use the existing install and grant lifecycle.
- **Home and input.** Integrate cards through [HomeRenderer.svelte](../src/lib/components/HomeRenderer.svelte) and the launcher's existing navigation. Render titles and feedback using Luma controls. Place first-version cards in a host-owned section that disappears when empty. Use stable focus IDs and move focus to a nearby control if a card disappears. When a plugin surface closes, return focus to the originating card if it still exists.
- **Dispatch.** Route Select through a native command dispatcher that checks the enabled package, declared command, current version, and grant at invocation. Resolve metadata without starting a WebView. Start the appropriate runtime on demand, wait for readiness, and deliver the command through the isolated bridge. Bound in-flight work and readiness waits, suppress duplicate activation while pending, and discard results from sessions invalidated by disable, update, or removal. Report activation failure on the invoking surface and make retry available.
- **Weather.** Declare an `openForecast` command and a Home card. Selecting the card opens the existing isolated forecast surface. Load data with the approved network bridge and existing location settings. Show loading, failure, and retry in the surface. Back closes it and restores Home focus. The initial release keeps card content static so rendering Home does not launch a runtime or fetch forecasts.

## Milestone 3 · Remote actions and reactive APIs

After the Home command path works, allow v3 phone remote panels to reference eligible commands from their own package. Start with actions whose behavior makes sense from a phone, such as playback control. Render controls on the host and retain the v1 remote panel format. Extend the [remote server](../src-tauri/src/remote/server.rs) and existing web remote panel flow to check pairing and current panel membership on every action, then use the same native dispatcher and grants as Home. Return pending, success, or failure to the phone. Display Box support requires a separate protocol decision.

Add settings-change notifications for a plugin's own resolved values and playback-state notifications under the corresponding read grants. Drive them from existing host changes, deliver them only to subscribed active sessions, and dispose subscriptions on shutdown or revocation. These events do not start idle plugins in this milestone. Specify event payloads, ordering relative to initial state, and duplicate handling in the SDK contract. Consider media-provider APIs when a concrete integration establishes the data, authentication, and lifecycle requirements.

## Acceptance and rollout

1. **Authoring.** From a fresh checkout, scaffold the example, press F5, and see it in a second Luma instance while the normal instance is running. Confirm app data and grants are separate. Save a valid edit and see it reload. Save an invalid edit and confirm the previous build still works and a precise error appears. Change declared access and confirm review is required.
2. **Distribution.** Validate and package the same build, then install it using the standard Settings dialog. Confirm approval is required, same-version changes are rejected for installed packages, and CLI, MCP, and import agree on shared validation cases. Confirm v1/v2 examples still install and behave as documented.
3. **TV and phone.** On TV, navigate to Weather, select it, exercise loading and retry, then press Back and verify focus. Disable, update, or remove the plugin during activation and verify pending work and the contribution disappear cleanly. For the remote milestone, use a paired phone and verify stale panel actions fail after disable or replacement.
4. **Resources.** Compare startup, Home idle, first activation, tray idle, and repeated open/close against the current app on Windows. A visible static card starts zero plugin runtimes and makes zero plugin network requests. An on-demand session releases its resources when closed. Use the [runtime acceptance record](CUSTOMIZATION-RUNTIME-SPIKE.md) for the measurement approach and agree on interaction and memory budgets from the baseline before release.

Land developer tooling first against the existing bridge, then deliver the Weather Home card with the first public v3 contract. Evolve the public package docs and SDK examples as each milestone ships. ZIP import and export remain the distribution workflow for these milestones.
